05 / AGENT BUILD

从 0 到 1，
搭一个 Agent。

Agent 不是给聊天机器人加一个更酷的名字，而是让模型在明确边界里观察、选择、行动、获得反馈，并知道什么时候应该停下来。

“Agent”这个词很容易让人联想到一个会自主完成所有事情的智能体，但工程上更准确的理解是：模型负责在当前上下文中决定下一步，工具负责改变外部世界，系统负责保存状态、限制权限和检查结果。

因此，一个值得搭建的 Agent 不应该从“让它更自主”开始，而应该从一个边界清楚、输入稳定、结果可验收的小任务开始。先做出最小闭环，再逐步增加记忆、并行和多角色协作。

Agent 的智能来自模型，Agent 的可靠性来自系统设计。

一、先定义一个足够小的 Agent

我选择的练习任务是“读取一份项目说明，列出需要确认的问题，并生成一份结构化任务清单”。它有明确输入，也有明确输出，不需要直接触碰生产数据。

要素定义为什么重要
输入项目目标、约束和已有资料减少模型凭空补全
工具读取文档、保存任务、查询状态让行动可被观察
输出问题列表、任务列表、依据和置信度方便验收和人工修改
停止条件完成、失败、超预算或需要人确认避免无限循环

这四个要素比“使用哪一个模型”更先决定系统能不能落地。模型可以更换，但输入输出合同和停止条件应该尽量稳定。

二、工具调用：让行动有明确的接口

如果让模型直接输出一段自然语言“我已经创建了任务”，系统无法知道它是否真的创建成功。正确做法是给它一个结构化工具：

{
  "name": "create_task",
  "description": "创建一条待办任务",
  "parameters": {
    "title": "string",
    "owner": "string",
    "dueDate": "string|null",
    "source": "string"
  }
}

工具定义要说明三件事：什么时候应该使用、参数必须满足什么格式、调用成功后返回什么。参数越含糊，模型越容易把行动变成一段看起来像行动的文字。

工具设计的最小原则

输入结构化、权限最小化、结果可验证、失败可重试、动作可撤销。不要一开始就给 Agent 一个“执行任意命令”的万能工具。

三、状态与循环：Agent 不是一次调用

01 / OBSERVE读取当前状态02 / DECIDE选择下一步03 / ACT调用工具04 / CHECK检查反馈

一个最小 Agent 可以被看成一个有限循环：

  1. 读取用户目标和当前状态。
  2. 让模型选择“回答、调用工具、请求澄清或停止”。
  3. 如果选择工具，校验参数并执行。
  4. 把工具结果写回状态，再进入下一轮。
  5. 达到完成、失败或预算上限时结束。

状态里至少应该包含目标、已完成动作、工具结果、待确认问题、错误信息和预算。不要只把完整对话历史无限塞回模型，长上下文会增加成本，也会让重要信息更难被注意到。

一个简单的预算

我会给每次运行设置最大 8 轮、最多 5 次工具调用、最长 2 分钟和固定 token 上限。达到任一上限就暂停，并把当前状态交给人处理。

四、没有评估，Agent 只是演示

Agent 的问题往往不是“能不能跑”，而是“十次运行有几次做对”。因此需要准备一组小型评测集，覆盖正常任务、缺少资料、工具失败、权限不足和用户中途修改目标等情况。

测试场景期望行为观察指标
资料完整生成任务并引用来源结构正确率、引用准确率
资料缺失提出澄清问题，不自行编造拒答质量、问题相关性
工具失败重试一次或清楚报告失败错误解释、重复调用次数
高风险动作暂停并请求人工确认拦截率、误执行率

每次修改提示词、工具定义或模型版本，都重新跑一遍这组测试。记录输入、模型选择、工具调用、最终输出和人工评分，才能知道系统到底是在进步还是只是在某个例子上变得更会说。

五、权限边界：让 Agent 知道什么不能做

权限应该从只读开始，再逐步增加。一个用于整理项目资料的 Agent，不需要发送邮件、删除文件或修改生产数据库。把工具分成只读、可写和高风险三类，并给高风险动作增加人工确认。

  • 只读：搜索资料、读取文件、查询状态。
  • 可写：创建草稿、保存任务、生成报告。
  • 高风险：发布内容、发送消息、删除数据、修改线上配置。

同时要记录“谁在什么时候以什么理由调用了什么工具”。日志不仅是出问题后的调查材料，也是评估 Agent 是否真的减少了工作量的基础。

六、从最小系统开始，再谈多 Agent

我建议的迭代顺序是：

  1. 一个模型 + 一个只读工具。
  2. 加入结构化输出和参数校验。
  3. 加入状态、预算和错误处理。
  4. 加入评测集和日志。
  5. 确认单 Agent 的边界后，再拆成规划、执行和审查角色。

多 Agent 不会自动带来更高质量。角色之间的交接会增加上下文成本，也会放大错误。只有当一个角色已经有稳定输入输出合同，拆分它才有意义。

我的起步清单

一个真实任务、一个只读工具、一个结构化输出、一个停止条件、一个评测集和一个人工确认点。把这六件事做好，已经足够建立第一个可靠的 Agent 原型。

Agent 的终点不是让人退出流程，而是把人的判断放到最有价值的位置：定义目标、处理例外、批准高风险动作，并持续改进系统的边界。
