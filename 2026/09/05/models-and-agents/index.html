03 / MODELS & AGENTS

模型与 Agent，
怎样一起工作。

大模型像不同专长的队员，Agent 像负责观察、规划、执行和复盘的工作角色。真正强大的系统，不是让一个模型包办一切，而是让能力在正确的位置协作。

“一个模型解决所有问题”是最容易理解的产品想象，但不一定是最好的工程方案。不同模型在速度、推理深度、长上下文、多模态、代码能力、成本和隐私边界上各有取舍；不同 Agent 也有不同职责，有的负责规划，有的负责查资料，有的负责调用工具，有的负责审查结果。

当这些角色通过清晰的输入输出合同连接起来，系统就不再只是一个聊天窗口，而是一支可以分工、交接和复盘的数字团队。

多 Agent 的重点不是“让更多模型说话”，而是让每一次协作都产生比单点回答更可靠的中间产物。

一、为什么需要模型与 Agent 协作

复杂任务通常同时包含几种不同性质的工作：理解目标、查找资料、做判断、生成内容、执行动作、检查质量。让一个模型从头做到尾，会出现三种问题。

  • 上下文混杂：规划、资料、代码和用户偏好全部塞在一个上下文里，模型难以保持重点。
  • 能力浪费：简单分类也使用最昂贵的推理模型，速度和成本都不理想。
  • 错误难定位：最终答案错了，却不知道是检索错、规划错、工具错，还是审查没有发现。

协作的价值，在于把大任务切成更小的责任单元。每个单元都可以有自己的模型、工具和验收标准，最终由编排层把它们组合起来。

二、各类模型如何分工

这里的“大模型”不专指某一个品牌，而是指系统可以根据任务选择不同能力档位。模型路由的目标不是永远选最强，而是在质量、速度、成本和数据边界之间找到合适的平衡。

模型角色适合处理常见取舍
快速通用模型分类、改写、摘要、简单问答、意图识别便宜、低延迟，但复杂推理能力有限
深度推理模型复杂分析、规划、代码设计、冲突判断质量较高，但成本和延迟更高
多模态模型图片、PDF、表格、语音、界面理解输入更丰富，但需要更严格的格式和隐私控制
代码模型代码补全、重构、测试、仓库级理解需要稳定的代码上下文和可运行的验证环境
本地或私有模型敏感资料、离线任务、低成本批处理数据更可控，但部署、速度和能力需要权衡

一个成熟的路由器应该先判断任务类型，再选择模型，而不是把所有请求都发给默认模型。它还要保留降级路径：当高能力模型不可用时，可以用较快的模型完成草稿，并把任务标记为需要复核。

模型之间要有“合同”

协作不应该依赖“大家看着办”。每个模型都要知道输入是什么、输出必须满足什么格式、失败时如何表达不确定性。例如研究模型输出资料卡片和引用，规划模型输出任务树，执行模型只接收结构化动作，审查模型输出问题列表和严重等级。

三、Agent 不是人格，而是责任边界

把 Agent 想象成“一个有名字的 AI 同事”很直观，但工程上更重要的是它负责什么、能访问什么、必须交付什么。一个 Agent 至少包含四个部分：目标、状态、工具和退出条件。

Agent 角色主要职责不应该做什么
Planner 规划者拆解目标、安排顺序、识别依赖和风险未经授权直接修改生产数据
Researcher 研究者检索资料、比对来源、标注证据和不确定性把推测包装成事实
Coder 执行者修改代码、运行测试、生成变更说明跳过测试直接发布
Reviewer 审查者寻找错误、检查约束、提出阻断意见为了让流程通过而降低标准
Operator 操作员调用外部系统、创建任务、发布结果越过权限和人工确认节点
Memory 记忆层保存偏好、决策、历史结果和可复用经验无边界地保存所有原始数据

角色数量不是越多越好。一个小任务也许只需要规划、执行和审查三个角色；只有当职责真的不同、上下文真的不同、评估真的不同，才值得拆成独立 Agent。

四、常见的协作模式

1. 串行交接：适合有明确依赖的任务

规划者先拆解，研究者补充资料，执行者完成动作，审查者检查结果。优点是流程清楚、容易追踪；缺点是任何一个环节变慢，整体都会变慢。

2. 并行协作：适合可以同时展开的任务

把一个问题交给多个研究 Agent，从不同来源或不同角度同时分析，再由汇总 Agent 合并结果。并行可以降低等待时间，但必须处理重复、冲突和输出质量不一致的问题。

3. 评审循环：适合质量要求高的任务

执行者生成初稿，审查者指出问题，执行者根据问题修改，直到满足验收标准或达到最大轮次。循环必须有明确的停止条件，否则 Agent 会在“再改一点”里消耗无限成本。

4. 专家会诊：适合高不确定问题

让不同专长的 Agent 分别给出判断，再由一个裁决角色比较证据和风险。这里的关键不是让模型投票，而是要求每个观点给出依据，让裁决过程可解释。

五、一个完整案例：AI 产品发布 Agent 团队

假设我们要把一个新功能发布到个人博客。目标不是“写一篇宣传文案”，而是从需求整理到线上检查，形成一条完整流程。

第一步：规划 Agent 读取目标

它把“发布一个新功能”拆成内容准备、页面修改、链接检查、视觉检查和发布说明，并标注哪些步骤需要人确认。它不直接写代码，只负责形成任务树和验收标准。

第二步：研究 Agent 补充上下文

它读取现有页面、历史文章、目标读者和设计规则，输出一份上下文包：应该使用哪些术语、哪些链接必须保留、哪些内容不能凭空补写。

第三步：代码 Agent 完成垂直切片

它只修改被授权的文件，先给出计划，再完成 HTML、CSS 或脚本变更，运行静态检查和链接检查，并把每个修改点写入变更说明。

第四步：审查 Agent 做三种检查

  • 内容检查：标题、描述和文章结构是否准确。
  • 技术检查：页面路径、资源引用、脚本语法是否正常。
  • 体验检查：移动端是否可读，焦点、对比度和跳转是否合理。

第五步：操作 Agent 等待人工确认

只有当测试和审查通过，且人确认了最终 diff，操作 Agent 才可以提交、推送或触发部署。发布后再由观察 Agent 请求线上页面，确认标题、资源和关键交互都正常。

这个流程看起来比“让一个模型直接改完”更长，但它把错误变得可见，把权限变得可控，也让失败后可以明确回到某一个环节。

六、协作系统最重要的是共享状态

多个 Agent 如果没有共享状态，就会反复做同一件事。共享状态不等于把所有聊天记录放进一个大文本框，而是要保存结构化信息：

  • 当前目标与验收标准；
  • 已完成的步骤和证据；
  • 仍然存在的假设、风险和阻塞；
  • 工具调用记录、权限范围和失败原因；
  • 需要人确认的决策点。

可以把它看成团队的项目看板。每一次交接都应该留下可读的中间产物，而不是只说一句“我已经处理好了”。

七、边界与治理：Agent 越聪明，系统越要克制

多 Agent 系统的风险不只是单个模型说错话，还包括错误被多个角色放大：一个错误假设被研究 Agent 当成事实，规划 Agent 把它写进任务，执行 Agent 真的调用工具，最终审查 Agent 因为上下文偏差而放行。

建议至少建立五个护栏

最小权限、结构化输入输出、关键动作人工确认、全链路日志、可撤销与回滚。任何不能解释、不能追踪、不能撤销的自动化，都不应该直接进入高风险环境。

还要给 Agent 设置预算：最大轮次、最大工具调用次数、最大 token、最大时间和最大影响范围。预算不是限制智能，而是让系统知道什么时候应该停下来求助。

八、从模型竞赛走向协作设计

未来的竞争不会只发生在“谁的模型更强”，也会发生在“谁能把不同模型组合得更合理”。一个快模型负责响应，一个强模型负责推理，一个多模态模型负责理解界面，一个私有模型负责处理敏感资料，再配合规划、执行、审查和记忆角色，才可能形成真正稳定的产品能力。

对个人开发者来说，最好的起点不是一上来搭建十几个 Agent，而是挑一个真实任务，明确一个输入输出合同，加入一个审查环节，再观察系统在哪一步产生了价值。协作是从分工开始的，但可靠性来自每一次交接都能被验证。
